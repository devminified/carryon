# Notifications

Carryon's primary notification channels are **Slack** (CO-409) and **Mattermost** (a follow-up, GitHub issue #113) — not email, there's no payroll-style transactional email need. Supabase Auth's built-in email (magic link, if ever enabled) is the only auth-related email; everything else goes to one or both chat platforms, sent directly by the Edge Function that caused the event.

## Slack (CO-409, as actually built) and Mattermost (#113, as actually built)

Per-project, optional, opt-in config lives in its own `project_notification_settings` table (`project_id`, `slack_webhook_url`, `mattermost_webhook_url`, `notify_digest`) — **not** new columns on `projects`, unlike `bucket`/`daily_token_budget`. Those are readable by any viewer (`members_can_read_their_projects`); a webhook URL lets its holder *post* into the team's channel, which is a materially different risk, so this table's own RLS is admin-only in every direction (select/insert/update/delete) — see `database-rls.md` and the migrations' own comments. A missing row means "notifications off" for that project, not an error — every reader here treats `maybeSingle()` coming back null that way. Both webhooks can be configured at once — `mattermost_webhook_url` is a second, independent, nullable column, not a `channel_type` enum, since a project isn't choosing one platform over the other. CO-410's admin Projects page (`web/src/modules/admin/ui/project-settings-form.tsx`) has a field for each; a project can also still be configured by hand via SQL, same manual-tuning shape `bucket`/`daily_token_budget`/`closed_at` already have.

**Slack and Mattermost are not payload-compatible** — confirmed against a real local Mattermost instance (`mattermost/mattermost-preview`), not assumed: Mattermost's incoming-webhook endpoint silently ignores Slack's Block Kit `blocks` array entirely (a message posted with that exact shape renders as nothing but the plain `text` fallback), but does understand Slack's older "attachments" shape (`{text, color}`), using its own Markdown dialect (`**bold**`, `[text](url)` links) rather than Slack's legacy mrkdwn (`*bold*`, `<url|text>`). This is why `_shared/mattermost.ts` is its own file with its own message builders, not a shared abstraction with `_shared/slack.ts` — see that file's own comment for the full reasoning. Every call site below fans the same underlying message data out to both configured webhooks independently (`Promise.all`, both senders already swallow their own failure and return a boolean rather than throwing) — a failed Slack post never blocks a Mattermost one, or vice versa.

Five message types. The three per-project ones (blocked-session alert, secret-rescan hit, daily digest) are each built twice — once by `_shared/slack.ts`, once by `_shared/mattermost.ts` — and fanned out to whichever of the project's two webhooks are configured; the two fleet-wide ones (compat CI, observability) stay Slack-only, below.

- **Blocked-session alert** — `_shared/summarize.ts`'s own `summarizeSession()` sends this itself, right after a successful write, but *only* on the transition **into** `outcome = 'blocked'` (the session's previous `outcome` wasn't already `'blocked'`) — otherwise the 30-minute cron sweep (or a CO-408 re-summarize) would re-send the same alert every time it still finds the session blocked. Named by the session's owner's GitHub login (`auth.admin.getUserById`, same lookup `list-sessions` already uses), the session's title, the blocked reason, and a link built from `WEB_APP_URL` (an Edge Function secret — see `.env.example`; the message degrades to no link, not a broken one, if it's unset).
- **Secret-rescan hit** — `rescan/index.ts` sends one message per hit, right after its own `audit_log` insert, reusing the same project's `project_notification_settings` lookup it already does for `bucket`. Never includes the matched secret value — only "rotate the affected credential" and a session link.
- **Daily digest (opt-in)** — a fourth scheduled Edge Function, `send-daily-digest`, same `x-cron-secret` + `pg_cron`/`net.http_post`/Vault shape as `rescan`/`sync-github-teams`/`purge-expired-sessions`/`summarize-session` (`edge-functions.md`), running once daily. Only for a project with `notify_digest = true` **and** at least one configured webhook — opt-in on top of having a webhook at all, since a team that only wants blocked-session alerts shouldn't get a daily message it never asked for. Groups the last 24 hours' sessions by developer (resolved the same way as the blocked alert); a project with zero activity in the window sends nothing at all, same reasoning as "projects with notifications off send nothing" — an empty digest every day trains a team to ignore the channel.
- **Claude Code compat CI failure (CO-503)** — `record-compat-run/index.ts` sends this on a failing nightly matrix leg, via a dedicated `COMPAT_CI_SLACK_WEBHOOK_URL` secret, deliberately **not** any project's own `project_notification_settings` webhook: this is about Carryon's own build going red on a given OS/Claude-Code-version combination, not an event belonging to a client project. No webhook configured just means no Slack post — the run is still recorded either way.
- **Observability alert (CO-504)** — `check-observability-alerts/index.ts` sends this on the false→true transition of any of its four alert conditions (a stale agent on a workday, cloud lag p95, the fleet upload error rate, abnormal per-project storage growth), via a dedicated `OBSERVABILITY_SLACK_WEBHOOK_URL` secret, same "Carryon's own ops, not a project's" reasoning as the compat-CI message above. Never re-notifies while an alert stays firing, and never posts on the true→false clear either — `observability_alert_state`'s own stored `is_firing` is what makes this symmetric with `_shared/summarize.ts`'s blocked-session alert (notify on enter, stay quiet on exit).

Never post transcript content to Slack — title, AI summary, and a link only. The summary itself is already AI-generated from redacted, condensed text (see `edge-functions.md`'s note on `summarize-session`), but Slack messages are the most widely-visible surface in the whole system, so treat them as the strictest filter, not a pass-through.

## Fallback email/SMS

If a future need arises (e.g. a digest email, an urgent security alert), follow the directory default: Supabase Edge Functions + Resend for email, Twilio via Edge Function for SMS. Not needed for anything currently in scope — don't add either until a ticket actually calls for it.
