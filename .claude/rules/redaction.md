# Redaction & Secret Handling (I5, NFR-07)

Binding rule: **no secret matched by the current rule set leaves the laptop**, for every session, every time. This is the first of the four security layers in Doc §"Security architecture" — everything downstream (RLS, signed URLs, audit log) assumes this layer already ran.

## Where it runs

`internal/redact`, called from `internal/upload` **before compression**. Redaction must run on every chunk, with no opt-out flag, no per-project exemption, and no "trusted repo" bypass. If a ticket proposes skipping redaction for performance, the answer is to make redaction faster, not to skip it.

## What it does (CO-301, as actually built)

- **Pattern matching:** `internal/redact`'s own hand-ported `regexp` rules (`rules.go`'s `DefaultRules()`, ~44 of gitleaks v8's own default patterns), gated behind a hand-written Aho-Corasick keyword prefilter (`ahocorasick.go`) — **not** the `github.com/zricethezav/gitleaks/v8/detect` library CLAUDE.md's locked stack literally names. Measured via `go list -deps`: importing that package pulls ~150 transitive packages (archive scanners, a TUI library, Viper's full config stack, a WASM regex runtime) for scanning plain JSONL text, none of it needed here. Confirmed with the user before proceeding (CLAUDE.md's "say so and propose a compliant alternative" — this *is* that alternative). The prefilter exists because checking all ~44 rules' keywords with 44 separate `bytes.Contains` calls per string value couldn't clear the 20MB/s throughput target on its own; a real trie-based automaton with `[256]int32` child arrays (not a `map[byte]int32` — measurably slower via Go's map hashing on this hot path) was needed once that simplification was shown not to hold up.
- **Path denylist:** whole tool results are dropped (not redacted-in-place) for paths like `.env`, private keys, and certificates — some content is denylisted entirely rather than scanned. Extensible from the server (see "Server-configurable overrides" below).
- **Overlap resolution:** when two rules' matches overlap (e.g. `generic-api-key`'s `"<label>-key: <value>"` shape ending right where a more specific rule's own match for the real value begins), the redacted span is extended to the union of every overlapping match, never shrunk to just one of them — a real bug here (discarding the longer, later match outright) left a secret's bytes completely unredacted, found via this ticket's own real-world NFR-07 validation and fixed in `resolveOverlaps`.
- **Entropy scan and 32MB overlapping-window streaming for oversized lines are not implemented in this build.** Honest status: CO-301's own testing points (the corpus suite, the throughput target, NFR-07's real-paste validation) never required either, and no line anywhere near 32MB has been observed in practice — per CLAUDE.md's "no speculative scale," building the window-splitting logic now would be solving a problem no current ticket has. If a future ticket hits a real need (a known secret format with no fixed pattern, or a transcript line that actually exceeds Go's practical in-memory JSON-decode size), build it then and update this line — don't assume it already exists because an earlier draft of this doc said so.

## Server-configurable overrides (`get-config`, CO-301)

`get-config` (no request body, any authenticated user) returns `{disabledRuleIds, denylistAdditions, pinnedVersion}` from the single `redaction_config` row — `pinnedVersion` (CO-308) is otherwise unrelated to redaction; see `internal/update`'s own doc comment for what it drives. `internal/redact.ApplyServerConfig(base, disabledRuleIDs, denylistAdditions)` merges that onto `redact.DefaultConfig()`: it can only **drop** a rule by ID or **add** a denylist glob — there is deliberately no field for a raw regex pattern, so a compromised or careless server-side change can narrow coverage but can never inject code this binary would execute against a developer's own transcript (see `Rule`'s doc comment in `rules.go`). The laptop (`cmd/carryon/agent.go`'s `lazyAPI.redactConfig`) caches the merged result for 24h, same pattern as `cachedClaudeVersion`, and falls back to the last known-good config (or plain `DefaultConfig()` before any successful fetch) on any error — I5 means a transient server/network failure must never cause an upload to go out with fewer protections than the built-in defaults.

## Rules for changing the rule set

- Every new or changed redaction rule needs a corresponding case in the redaction corpus test suite before it merges — a rule with no test proving it fires (and no test proving it doesn't over-fire on legitimate content) doesn't ship.
- Widening what's considered "safe to pass through" (a new exemption, a narrower pattern) is a security-sensitive change — treat it like an RLS policy change: it needs the same scrutiny as loosening a `using` clause.
- Never log the matched secret itself, even at debug level, even locally. Log that a redaction fired, the rule ID, and the location — never the value.

## Server-side rescan is a backstop, not the primary defense (CO-306, as actually built)

A nightly `rescan` Edge Function re-scans chunks uploaded in the last 24 hours (or, for a manual full rescan after a rule update, every chunk the "needs rescanning" predicate below still matches) against the server's current rule set — `_shared/redact.ts`, a hand-kept TypeScript port of `internal/redact/rules.go`'s own patterns (same rule IDs; see that file's own header comment for why the laptop's Aho-Corasick prefilter and JSON-walk aren't ported, and why a plain `JSON.parse`/`JSON.stringify` round trip is this file's much simpler stand-in for walk.go's explicit-stack token walker). On a hit, in order: **rewrite** the chunk's Storage object in place with the secret redacted (same object key, same `byte_start`/`byte_end` — those still describe the original file, same as the laptop's own CO-301 redaction; a new `sha256` matching the rewritten plaintext), **log** a `rescan_hit` row to `audit_log` (the real, durable notification surface today — see edge-functions.md's own note on why push notification via Slack/email is deferred to CO-409, not built ahead of its own ticket), and a structured `console.warn` naming which rule fired (never the matched value). The actual key rotation is a human action the notification is meant to prompt, not something this job does itself — there is no way to automatically rotate an arbitrary third-party credential.

A chunk "needs (re)scanning" whenever `session_chunks.last_rescanned_at` is null, or predates `redaction_config.updated_at` (the rule set has changed since) — this single predicate is also what makes a batch resumable with no cursor: a chunk this run already updated drops out of every later run's `WHERE` clause by construction, so a timeout partway through a batch just leaves the remainder for the next invocation.

The rescan existing does not justify loosening laptop-side redaction; it exists because rule sets improve over time and old chunks were scanned under an older rule set, or because a secret reached Storage by some path other than the laptop's own upload pipeline entirely (this ticket's own testing point — verified for real by planting a secret directly via a service-role Storage PUT, bypassing `internal/upload` altogether, and confirming `rescan` found and redacted it).

Reading and rewriting a chunk's actual bytes is this codebase's one deliberate exception to "bytes bypass the API" (I9, architecture.md): I9 keeps the server out of the laptop's own upload/download path, not out of its own background maintenance over data it already owns, with no laptop waiting on the call.

## Signed URLs

Every signed URL (upload or download) is scoped to one object and one HTTP method, and expires in **5 minutes or less** (NFR-07, I6) — with one verified, platform-level exception: Supabase Storage's upload signed URLs (`createSignedUploadUrl`, used by `register-chunk`/CO-110) have a fixed **2-hour** expiry with no `expiresIn` option, confirmed against a live local instance (both the SDK and the raw `/object/upload/sign/...` endpoint ignore an `expiresIn` body field entirely — there is no config.toml knob for it either). Download signed URLs (`createSignedUrl`, used by `get-manifest`/CO-203) *do* support `expiresIn` and must stay at 5 minutes or less — this exception is upload-URL-only. A longer TTL "to make testing easier" doesn't ship — fix the test instead; this one exception is a documented platform limit, not an opt-out pattern to reuse elsewhere without the same verification.

Upload signed URLs for a chunk's object key must be requested with `{upsert: true}` (`x-upsert: true` header — the SDK's `createSignedUploadUrl(path, {upsert: true})` sets this correctly; a raw request needs the header, not a body field) — verified against a live instance that *registering* a signed URL for an existing key 409s (`KeyAlreadyExists`) without it. This is what makes retrying a chunk upload (same `session_id`/`seq`, e.g. after `confirm-chunk` failed despite the `PUT` succeeding) safe rather than hitting a wall at the sign step (I3).

An Edge Function's `createSignedUploadUrl(...).data.signedUrl` bakes in that function's own `SUPABASE_URL` env var — inside Docker (local dev) this is an internal hostname (`http://kong:8000`), unreachable from the laptop making the actual `PUT`. The *token* itself (`data.token`) carries no host claim, only the object path, scope and expiry, so `register-chunk` (CO-110) returns the token, not the full URL, and the laptop client builds its own upload URL from its own already-correct `api_url`. Found by a real `PUT` failing DNS resolution on `kong` from outside Docker, not assumed — the same caution applies to any future Edge Function that hands a Storage URL back to a laptop client.

**Per-project buckets (CO-305).** Most projects share one default bucket (`carryon-sessions`), but a project can have its own dedicated bucket (`projects.bucket`, see `database-rls.md`) for a client whose contract requires physical separation. Every function that signs a chunk/snapshot URL looks up the project's `bucket` via `_shared/storage.ts`'s `resolveBucket()` and returns it alongside the token (`RegisterChunkResult.Bucket`, `ManifestChunk.Bucket`, `ManifestSnapshot.Bucket`, `SignSnapshotBundleResult.Bucket`) — the laptop client builds the actual upload/download URL from *that* bucket, never a hardcoded one, via `Client.StorageUploadURL`/`StorageDownloadURL`'s `bucket` parameter. Both the shared and any dedicated bucket are private with a `file_size_limit` (10MiB on `carryon-sessions`, set directly via SQL `update storage.buckets` in CO-305's migration — a chunk's own cap is 8MiB uncompressed, plus a safety margin for an oversized single line or redaction inflation); creating a dedicated bucket is a manual, one-time ops action, the same pattern as the GitHub OAuth App and GitHub App setup in `auth.md` — there's no Edge Function for it.
