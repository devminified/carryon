# Edge Functions (Supabase, Deno/TypeScript)

The named RPCs: `register-session`, `register-chunk`, `confirm-chunk`, `end-session`, `get-manifest`, `register-snapshot`, `summarize-session`, `rescan`, `sync-github-teams`. One directory per function under `supabase/functions/`.

`sign-snapshot-bundle` (CO-202) joins this list as a narrow exception to "one function per RPC, named up front in the build plan": it exists purely because `register-snapshot`'s git-bundle fallback path needs a signed Storage upload URL before it has anything to register, the same two-phase shape `register-chunk`/`confirm-chunk` already has for chunks. It signs only — `register-snapshot` is still the one function that ever writes a `code_snapshots` row, for both the ref and the bundle path.

`list-sessions` (CO-204) isn't in that original list either — it exists because `carryon ls` needs to list every session the caller can see across all of their projects. Since CO-302 landed real RLS, its `projects`/`sessions` reads run as the caller directly (`callerClient`) — RLS alone restricts the result to exactly what that user can see, no hand-computed membership list needed. Only the owner GitHub-login lookup (`admin.auth.admin.getUserById`, the `auth` schema isn't exposed to PostgREST — see `auth.md`) still needs the service role.

`register-fork` (CO-208) is the last of these — it creates the `sessions` row for a pulled/forked session (`parent_session_id` set, `status: 'live'`, owned by the puller). The puller's identity always comes from their own JWT, never a client-supplied field — the same reasoning as every other identity-sensitive write in this codebase. The session-ID rewrite inside the pulled transcript's own file happens entirely on the puller's laptop (`internal/pull.RewriteSessionIDFile`); this function is only the server-side bookkeeping so the fork's own agent has a row to upload into once the puller resumes.

`get-config` (CO-301) is the same kind of named exception: it lets `internal/redact`'s laptop-side rule set be narrowed (disable a rule by ID) or its path denylist extended, from the server, without a new binary release. No request body, and no project/role check — every authenticated user gets the same global config, since there's no per-project redaction config in the current build plan. It reads the single `redaction_config` row with the service-role client — this one stays on the service role even past CO-302, since `redaction_config` has no per-project scoping for RLS to key off at all (every authenticated caller gets the same global row) — and returns `{disabledRuleIds, denylistAdditions, pinnedVersion}` — see `.claude/rules/redaction.md` for why there's deliberately no way to supply a raw pattern through it, and `pinnedVersion`'s own doc comment in `get-config/index.ts` for why CO-308's otherwise-unrelated version pin lives on this same response.

`confirm-pull` (CO-304) — the laptop calls it once `carryon pull` has fully succeeded, writing `audit_log`'s `"pull_complete"` row. It exists because the server has no other way to know a pull finished: chunk bytes flow straight from Storage to the laptop (I9), never through the API, so `get-manifest`'s own `"pull_manifest"` row only ever covers the *start* of a pull. Same access rule as `get-manifest` (resumer role or higher): the session-existence check stays on the service role (so a missing session reports a clean 404, not folded into the 403 a real-but-forbidden session gets), and the role check itself runs as the caller via CO-302's own `project_members` select policy.

`get-session-transcript` (CO-403) is the last of these — it backs the web session viewer (`/sessions/[id]`). Deliberately **not** `get-manifest` reused with a lower role check: `get-manifest` hands out a code snapshot's download/ref alongside chunks, which only pull/resume needs (auth.md's access table — a `viewer` can read transcripts but never pull/resume); bending one function to serve two different role floors would make its own access rule read wrong at the call site. So this is its own function, gated at `viewer` role (not `resumer`), handing out only transcript chunks (every stream, main and any subagents, each with its own short-lived signed download token — same shape as `get-manifest`'s chunk list) plus the session's own metadata and its forks, for the side panel. Audits `"view"` (the exact action name `audit_log`'s own CO-304 migration comment already reserved for "Phase 4's web transcript viewer") — once per real page open, not deduplicated like `upload`'s.

`get-session-family` (CO-404) backs the session viewer's fork lineage tree in the side panel. Same `viewer`-role floor as `get-session-transcript`, but it writes no audit row of its own — `get-session-transcript`'s own `"view"` row already covers "opening the page" for the same request; this is supplementary tree data for that same open, not a second audited visit. It's a plain iterative walk (via the service role): up from the requested session to find its root (stopping at a null `parent_session_id`, a cycle, or a dangling reference with no matching row — a real case since CO-307's retention sweep deletes session rows outright, though the schema's own `parent_session_id … references sessions on delete set null` FK means that specific dangling state can't actually arise through normal deletion; the walk still defends against it), then down (BFS) to collect the whole subtree — capped by `MAX_HOPS`/`MAX_NODES` against a hypothetical cycle or runaway tree. Deliberately **not** a recursive SQL CTE or a new Postgres function: CLAUDE.md's "no speculative scale" for what's realistically a handful to a few dozen nodes per session. Every fork inherits its parent's `project_id` by construction (`register-fork`'s own upsert, CO-208), so the whole family tree is always one project in practice — but the response's per-node `accessible` flag is still a real per-node RLS check (via the caller's own client layered on top of the admin-client structural walk), not an assumption, covering the ticket's own "forks the viewer can't access" case if that invariant is ever relaxed. An inaccessible node carries only its `id`/`parentId`, never its title/owner/timestamp.

`rename-session` (CO-405) is `carryon rename <id> "<title>"`'s backend — the laptop's only path to renaming a session, since it never touches Postgres directly (three trust zones, architecture.md). The web app's own rename goes straight through a Server Action + the cookie-bound client instead (`modules/sessions/data/actions.ts`'s `renameSessionAction`), since that surface already holds a real session; this function exists purely for the CLI. Either the session's own owner or an admin of its project may rename it — a manual server-side ownership-or-admin check runs first (so a non-owner, non-admin caller gets a clean 403), then the actual update runs as the **caller** (`callerClient`), with RLS (`owner_can_update_their_sessions` OR this ticket's `admins_can_update_sessions`) as the real enforcement — same architectural shift `delete-session`/`list-sessions`/`get-manifest`/`register-fork` already made. Always stamps `title_source = 'manual'`, so CO-407's not-yet-built `summarize-session` never silently overwrites a developer's own title.

`rescan` (CO-306, built as the second real scheduled Edge Function after `sync-github-teams`) is the one function in this codebase that reads and rewrites bytes it already owns in Storage, rather than only ever handing out metadata or signed URLs — see `.claude/rules/redaction.md`'s own rescan section for the full detail (its rule-matching port in `_shared/redact.ts`, the zstd codec in `_shared/zstd.ts`, and why that's a deliberate, narrow exception to I9 rather than a violation of it: I9 is about keeping the server out of the laptop's own upload/download path, not about forbidding its own background maintenance over its own stored data with no laptop waiting on the call).

`purge-expired-sessions` (CO-307) is the third scheduled Edge Function, same `x-cron-secret` shape — a daily sweep that purges a closed project's session data (sessions, chunks, code snapshots, their Storage objects, and every `audit_log` row for that project) once `retention_days_after_close` has elapsed since `closed_at`. Accepts `{"dryRun": true}` to report what it would delete without deleting anything (this ticket's own CTO-sign-off validation point — see `docs/co-307-retention-dry-run.md`). Deliberately does NOT delete a session's `refs/carryon/*` git ref via the GitHub API as the ticket describes — Carryon's real GitHub App (CO-303) has no write permission to any repo, and expanding it was explicitly deferred by the user rather than done silently; see the function's own doc comment.

`delete-session` (CO-307) is `carryon admin delete <sid> --reason`'s backend — an immediate, explicit single-session delete, admin-only, with a mandatory reason recorded in `audit_log` as the only remaining record. Unlike most functions in this list, its actual `sessions` row delete runs as the **caller** (`callerClient`), not the service role — CO-302's own `admins_can_delete_sessions` RLS policy was written with this function in mind (see that policy's own comment), so RLS is the real enforcement for that one write, the same architecture shift `list-sessions`/`get-manifest`/`register-fork` already made. The earlier manual role check still has to run first regardless, since removing the session's Storage objects has no RLS to lean on at all.

## Contract

```ts
// supabase/functions/register-chunk/index.ts
import { z } from 'npm:zod@4.6.7'; // pin an exact version — deno lint's no-unversioned-import is not optional

const Input = z.object({
  sessionId: z.string().uuid(),
  seq: z.number().int().nonnegative(),
  byteStart: z.number().int().nonnegative(),
  byteEnd: z.number().int().positive(),
  sha256: z.string().length(64),
});

Deno.serve(async (req) => {
  const parsed = Input.parse(await req.json()); // throws on invalid input — caught by the top-level handler
  // ... RLS-scoped insert, using the caller's JWT, never the service key
});
```

Rules:

1. **Zod-validate every input.** No free-form casting of the request body.
2. **Run with the caller's JWT**, never the service-role key — except queue workers, which use a narrowly scoped role (Doc §"API hardening"). If a function seems to need the service key to "just work," that's a sign it belongs behind RLS instead.
3. **Idempotent on `(session_id, seq)`** (or the equivalent key for the function) — a retried call must be a safe no-op, not a duplicate (I3). `register-chunk` and `confirm-chunk` in particular must tolerate at-least-once delivery.
4. **Size and schema limits enforced**, not just typed — a Zod schema with no `.max()` on a string isn't enough on a public ingress function.
5. **Rate limiting:** token bucket per user and per project (Doc §"API hardening"). Required before any function is reachable without a prior narrower check.
6. **Structured logs only** — log the session ID and the step, never the chunk's content or a raw transcript line.
7. **Response shape is stable** — same success/error envelope across functions.

## How background work actually runs here

The current build plan has no queue or outbox — it's two patterns, both already named in specific tickets:

- **Triggered directly from the request handler that caused it.** `end-session` (CO-111) is what flips a session to `ended`; `summarize-session` (CO-407) is "triggered on `end-session`" — i.e. `end-session` invokes it, synchronously or fire-and-forget, not through an intermediate queue table.
- **Scheduled (cron) Edge Functions** for periodic work: `sync-github-teams` runs every 15 minutes (CO-303, the first one actually built — see below for the real pattern), the secret rescan runs nightly (CO-306), live-session re-summarization runs every 30 minutes (CO-407). There's no persistent job queue to feed.

  **The real wiring, as CO-303 built it** (verified against a live local instance, `net.http_post`'s async response landing in `net._http_response`): `pg_cron` doesn't call an Edge Function directly — it schedules a plain SQL job that calls `net.http_post` (the `pg_net` extension) against the function's own URL (`http://kong:8000/functions/v1/<name>` from inside the Postgres container — the same internal-hostname caveat `redaction.md`'s signed-URL section documents). A pg_cron job's SQL can't read an Edge Function secret directly, so the shared authentication value lives in **Supabase Vault** (`vault.create_secret`/`vault.decrypted_secrets`) and is passed as a custom header; the function checks that header in code instead of a caller JWT, since there's no user to verify (`config.toml`'s `[functions.<name>] verify_jwt = false` turns off Kong's own JWT gate, which would otherwise reject a request carrying no JWT at all — see `auth.md`'s GitHub App section for the full example). Vault and the function's own secret are two different systems with no automatic bridge, so a human has to set both to the same value once per environment — document that step directly in the migration that schedules the job, the same way CO-303's own migration does.
- **Scheduled, but not an Edge Function at all**, when the job is pure SQL: CO-111's idle-session sweep (ending a session with 12 hours of no activity) is `pg_cron` calling a plain Postgres function directly — no Deno runtime, no HTTP hop, nothing to deploy separately. See `.claude/rules/database-rls.md`'s "Scheduled jobs that are pure SQL" for the pattern (including the default-`PUBLIC`-`EXECUTE` footgun it has to guard against). Reach for this instead of a scheduled Edge Function whenever the job needs nothing Postgres itself can't already do.

**Not part of the current build plan:** an outbox table, a queue (pgmq or otherwise), and worker processes are Doc §"Asynchronous work" (Tier 1/2+ scaling), not anything a 52-ticket build-plan item asks for. If a ticket introduces real queueing (high enough chunk volume that a synchronous call from `confirm-chunk` becomes a bottleneck), build it then — don't pre-build the outbox plumbing now.

## `summarize-session` and the Anthropic API

The only Edge Function that calls an external AI provider. It receives already-redacted, already-condensed text — never a raw transcript line, and never anything that bypassed `internal/redact` on the way up. See `.claude/rules/redaction.md` for what "already redacted" guarantees and what it doesn't.

`summarize-session` doesn't exist yet (CO-407) — but the module that will do its "condensed text" step does: `_shared/condense-transcript.ts` (CO-406). It reads a session's main-stream chunks from Storage (`readSessionMainChunks`, the same download-then-decompress shape `rescan` already uses), groups the parsed entries into turns (a real developer prompt through to the next one), and renders each turn as the developer's prompt in full, one line per tool call (tool, target, result status — never a tool's raw output), and Claude's final text reply, plus the deduplicated files-touched/commands-run lists. `applyTokenCap` then drops the oldest *middle* turns first (always keeping the first and last) to stay under ~60,000 tokens, in a single linear pass over the turns — not repeated re-scans, which would be the first thing to fall over on a genuinely large session. Supports incremental mode (`afterSeq`): condensing a later range of chunks on its own produces exactly the turns found in that range, so an earlier range's turns concatenated with a later range's turns equal condensing everything in one call — *provided* the cut lands on a turn boundary, which is CO-407's own seq-bookkeeping job to uphold, not something this module can enforce from inside one call. Never expands a `[REDACTED:…]` placeholder or reconstructs text around one — every string it touches is copied verbatim from the parsed transcript.
