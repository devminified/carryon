# Database & RLS

## Migrations

- All schema changes are SQL migrations under `supabase/migrations/`. Never click around in the Supabase dashboard to change schema.
- Filename format: `YYYYMMDDHHMMSS_short_description.sql`.
- Each migration enables RLS on every new table **in the same file** that creates it.
- `supabase db lint` and a full apply-to-fresh-database run gate every PR (see `.claude/rules/testing.md`).

## Schema (current build plan — CO-102)

A project **is** the tenant boundary here: there's no separate organization/`tenant_id` column. Access is scoped by `project_members` membership, checked via `has_role()` below. Six tables, exactly as CO-102 specifies (Doc §"Database recommendation"):

| Table | Primary key | Notes |
| --- | --- | --- |
| `projects` | `id` | one row per registered repo; `git_remote` unique; `team_viewer`/`team_resumer`/`team_admin` (added by CO-303's migration) are GitHub's own stable numeric team IDs, nullable — a project with none set stays 100% manually managed; `bucket` (nullable text, added by CO-305's migration) is a dedicated Storage bucket for a client whose contract requires physical separation — null means the project uses the shared default bucket (`carryon-sessions`); creating the bucket itself and setting this column are both manual, one-time ops actions, not automated by any Edge Function; `closed_at` (nullable timestamptz, added by CO-307's migration) and `retention_days_after_close` (int, default 90) drive the daily retention sweep — null `closed_at` means active, never touched; setting `closed_at` is itself a manual, one-time admin action today, same shape as `bucket` — there's no admin UI yet (Phase 4) to drive it from; `daily_token_budget` (int, default 200000, added by CO-407's migration) caps `summarize-session`'s own daily Anthropic spend per project (real input+output tokens, summed from `ai_usage`, not dollars) — same manual-tuning shape as `retention_days_after_close`, no admin UI yet either |
| `project_members` | `(project_id, user_id)` | `role` is `viewer` / `resumer` / `admin`, mirrored from GitHub teams (CO-303); `source` (`'manual'` \| `'sync'`, added by the same migration) marks whether a row was an admin's own direct action or the sync job's — the sync job only ever writes/removes `'sync'` rows, so a manual override always survives the next sync |
| `sessions` | `id` | `id` is Claude Code's own `session_id`; `parent_session_id` set on a pulled fork; `ended_reason` (`'explicit'` \| `'idle'`, added by CO-111's migration) distinguishes a real `SessionEnd` from the idle sweep below; `search_vector` (generated `tsvector` over `title`+`summary`, GIN-indexed, added by CO-402's migration) backs the web session list's free-text search — a generated column rather than an expression index, so a cursor-paginated search query can reference it directly instead of repeating `to_tsvector(...)` in every clause; the table is also added to the `supabase_realtime` publication by that same migration, so the web list updates live — RLS still gates what a given subscriber actually receives, same as any other read; `title_source` (`'ai'` \| `'manual'`, default `'ai'`, added by CO-405's migration) is set to `'manual'` by every real rename path (`rename-session`, the web app's `renameSessionAction`) — `summarize-session` (CO-407) checks this is still not `'manual'` before ever overwriting `title`; `pinned` (boolean, default `false`, same migration) sorts a project's session list pinned-first (`sessions_pinned_last_activity_idx`); `blocked_reason` (nullable text, added by CO-407's migration) is only ever set alongside `outcome = 'blocked'`; `summarized_through_seq` (nullable int, same migration) tracks how far into the session's main stream `summarize-session` has already condensed and summarized — null means never summarized, and it's what makes that job's own incremental mode (CO-406) possible; `embedding vector(384)` (added by CO-501's migration, HNSW-indexed with `vector_cosine_ops`) is the session-level semantic-search vector — `summarizeSession()` REPLACES it on every summary run (merged into that same `update` call, not a second write — see `_shared/summarize.ts`'s own comment), unlike `session_passages` below; `files_touched` itself predates this (CO-406/CO-407's own condensed-transcript extraction) but gets a GIN index from CO-502's migration (`sessions_files_touched_gin_idx`) — see `find_sessions_by_file` below for the "who touched this file" lookup it backs, and `files_touched`'s own cross-machine path normalization |
| `session_passages` | `(session_id, seq)` unique, `id bigserial` pk | added by CO-501's migration; per-turn chunks of the condensed transcript (CO-406's own `turns`), embedded incrementally and ACCUMULATED (never replaced — append-only, I2) since a turn is immutable once Claude Code writes it, unlike the session-level `embedding` above which really is a rolling summary; `seq` continues from the existing per-session passage count, written by `summarize.ts`'s own `embedNewPassages()`. RLS mirrors `sessions`' own `owner_or_member_can_read_sessions` exactly (a passage is exactly as visible as the session it's a turn of) — one `select` policy, no insert/update/delete policy for anyone but the service role (`summarizeSession` is the only writer, same shape as `ai_usage`) |
| `session_chunks` | `(session_id, stream_id, seq)` | append-only, grows forever within a session; `stream_id` is `'main'` for the session's own transcript or a subagent's `agent_id` for a child stream (CO-109/CO-110 — added by a later migration than CO-102's original `(session_id, seq)`, once a real subagent chunk would otherwise have collided with the main stream's `seq` numbering); `last_rescanned_at` (nullable timestamptz, added by CO-306's migration) is the one narrow exception to this table's append-only-bytes rule — `rescan` overwrites a chunk's object in place and updates its `sha256` when a hit is found, since the whole point is closing a security hole, not preserving a byte history of it |
| `code_snapshots` | `(session_id, seq)` | `wip_ref` (hidden git ref) or `object_key` (bundle fallback, CO-202); `tree_sha` (added by a later migration than CO-102's original columns, CO-201) is the pushed commit's tree object, letting a retry compare against what's already registered without re-deriving it server-side |
| `audit_log` | `id bigserial` | append-only; RLS blocks `DELETE` for everyone but the DB owner; `project_id`/`ip`/`user_agent` (added by CO-304's migration) — `project_id` is deliberately **not** a foreign key, same as the original `session_id` column, so a row outlives the project/session it's about once CO-307's retention job starts deleting rows (an enforced FK here blocked every project delete in the real local e2e pull test — fixed by removing it, not by cascading); `reason` (nullable text, added by CO-307's migration) is the mandatory reason an admin gives to `carryon admin delete <sid> --reason` — the only other current writer of it; every other action type leaves it null |
| `ai_usage` | `id bigserial` | added by CO-407's migration; append-only (I2) — one row per real Anthropic API call `summarize-session` makes, successful or not; `project_id`/`session_id` **are** real foreign keys (`session_id` nullable, `on delete set null` — unlike `audit_log`, a usage row isn't itself about the session's own data retention, so there's no CO-307-style delete conflict to avoid); `cost_usd` is informational only, from a documented-as-approximate static rate (`_shared/anthropic.ts`) — the daily budget cap itself sums real token counts, not this column |
| `project_notification_settings` | `project_id` | added by CO-409's migration; one optional row per project — `slack_webhook_url` (nullable text) and `notify_digest` (boolean, default false). **Not** columns on `projects` itself, unlike `bucket`/`daily_token_budget` (readable by any viewer): a webhook URL lets its holder *post* into the team's Slack channel, not just read something, so this table's own RLS is admin-only in every direction (select/insert/update/delete), never widening `members_can_read_their_projects`. A missing row means "notifications off" — every reader (`summarize.ts`, `rescan/index.ts`, `send-daily-digest/index.ts`) treats `maybeSingle()` coming back null that way, not as an error. CO-410's admin Projects page is this table's only writer now (via the web app's own service-role client, not RLS — see auth.md's `requireGlobalAdmin()`); its own RLS policies above exist for a future direct-PostgREST write path, not one that's wired up yet. |
| `agent_heartbeats` | `(user_id, machine_id)` | added by CO-410's migration; the laptop's own periodic "I'm alive" check-in (`cmd/carryon`'s `runHeartbeatLoop`, every 5 minutes), backing the admin "Agents" page. `hostname`/`version`/`blocked_sessions`/`last_seen_at`. Keyed by machine, not just developer, since one person can run the agent on more than one machine. RLS: `self_can_upsert_own_heartbeat`/`self_can_update_own_heartbeat` (`user_id = auth.uid()`) are the real write enforcement (the `heartbeat` Edge Function runs as the caller, CO-409/CO-410's architectural shift continued); `any_project_admin_can_read_heartbeats` (`is_any_project_admin()`, below) is the real read enforcement — no delete policy, a stale machine's row just ages out by `last_seen_at` — CO-504's own `purge_stale_heartbeats()` (below) is what actually removes it after 30 days now, rather than forever. CO-504's migration adds `os`/`bytes_behind`/`last_upload_at`/`upload_attempts`/`upload_errors`/`redactions_applied` — all optional in the Zod schema (an older agent binary hasn't shipped them yet) and all reset to 0/null by `internal/upload.Uploader.TakeCounts` on every real heartbeat, so they reflect the interval since the *last* heartbeat, not an all-time total. |
| `storage_snapshots` | `(project_id, snapshotted_at)` | added by CO-504's migration; one row per project per day, written by `check-observability-alerts` from the real `project_storage_totals()` function (summed from `sessions.total_bytes`) — the "yesterday vs. today" baseline `abnormal_storage_growth_project_ids()` (below) needs, since there's no other history of a project's own storage size over time anywhere in this schema. RLS: `any_project_admin_can_read_storage_snapshots` only — service role is the sole writer. |
| `observability_alert_state` | `alert_key` | added by CO-504's migration; one row per alert (`stale_agent`, `lag_p95`, `error_rate`, or a per-project `storage_growth:<project_id>`), tracking whether it's *currently* firing — `check-observability-alerts`' own "fire once, clear quietly" gate (see that function's own comment, and `_shared/summarize.ts`'s blocked-session alert for the precedent this mirrors). RLS: `any_project_admin_can_read_alert_state` only — service role is the sole writer. |
| `claude_compat_runs` | `id bigserial` | added by CO-503's migration; append-only (I2) — one row per (`carryon_version`, `claude_code_version`, `os`) the nightly compatibility workflow tests, written only by `record-compat-run` (service role, authenticated by a shared CI secret, not a user JWT or `project_members` role at all). `version_label` (`'pinned'` \| `'latest'`) is what the web app's own pinned-version gate (`web/src/modules/admin/data/actions.ts`, `lib/compat.ts`'s `isCompatClean`) actually matches against — the real resolved `claude_code_version` is kept alongside it for the ticket's own "flagged with a specific breaking change" validation point, not for the gate. RLS: `any_project_admin_can_read_compat_runs` (`is_any_project_admin()`) is the only policy — no insert/update/delete policy for anyone but the service role. |

Indexes (CO-102): `sessions(project_id, last_activity_at desc)`, `sessions(user_id)`, `session_chunks(session_id, stream_id, seq)` (via the primary key). CO-304 adds a partial unique index enforcing "upload" is logged at most once per session per UTC day (`audit_log_one_upload_per_session_per_day`, keyed on `(session_id, (at at time zone 'utc')::date)` — `date(at)` alone isn't IMMUTABLE enough for an index, since its result depends on the session's timezone setting).

**Not part of the current build plan:** `tenant_id`, partitioning, `session_manifests`/compaction, `leases`, and `outbox` are all Doc §"Scaling to millions of users" (Tier 2/3) concerns — real, but deliberately out of scope until a ticket actually calls for them (CLAUDE.md: "No speculative scale"). Don't add a `tenant_id` column or a leading-key convention pre-emptively; if a future ticket introduces multi-org tenancy, it'll say so and this file gets updated then, not before.

## Scheduled jobs that are pure SQL, not an Edge Function

CO-111's idle-session sweep (a session with no activity for 12 hours gets `status = 'ended', ended_reason = 'idle'`) is a `pg_cron` job calling a plain SQL function directly — `end_idle_sessions()` — not an Edge Function, because the whole state transition is a single `UPDATE` with no Storage/API call involved (see `.claude/rules/edge-functions.md`'s "no queue/outbox" pattern: this needs even less than an Edge Function). Two things any similar future job must get right, both already done here:

- **`revoke execute on function … from public`** right after creating it. Postgres grants `EXECUTE` on a new function to `PUBLIC` by default, which would otherwise let `anon`/`authenticated` trigger it over PostgREST at `/rest/v1/rpc/<function>` — a scheduled job's SQL is an implementation detail, not an API surface. Verified locally: after the revoke, `information_schema.routine_privileges` lists only `postgres`.
- **`security definer` + `set search_path = public`**, same as every other `SECURITY DEFINER` function in this file.

CO-504's `purge_stale_heartbeats()` (daily, 05:00 UTC) is the second one of these — `agent_heartbeats` rows older than 30 days are deleted outright, a single `DELETE` with nothing to upload or sign, same reasoning as `end_idle_sessions`'s own single `UPDATE`.

## RLS policies

Every table has RLS **enabled**. CO-102 shipped every table with RLS on and deny-all; CO-302 (`supabase/migrations/20261108010000_add_roles_and_rls.sql`) is what added the real per-role policies, built around one helper (exact signature per Doc §"Row-level security that stays fast"). The full table-by-role matrix (and how each cell is actually verified) lives in `docs/co-302-role-matrix.md`; note that doc predates CO-304, so its `audit_log` row (which still says "deliberately deferred") is superseded by this section.

`audit_log`'s own real policies (CO-304, `supabase/migrations/20261108030000_add_audit_log_columns_and_rls.sql`) are two separate `select` policies, not one: `has_role(project_id, 'admin')` for a project's admins (every row), and a second policy for a non-admin who owns the session a row is about (`session_id is not null and (select user_id from sessions where id = session_id) = auth.uid()`) — a `role_change`/`config_change` row has no `session_id` at all, so that second policy correctly never surfaces those to anyone but an admin. No insert policy exists (every current writer already holds the service role for an unrelated reason in the same request); no update/delete policy for anyone, including admins — append-only (I2), only CO-307's retention job (service role) ever removes a row.

`project_members.role` is a Postgres **enum**, not plain `text` — `viewer < resumer < admin` only holds under `>=` if declared in that order (`text` would sort `'admin' < 'resumer' < 'viewer'`, the opposite of what's intended):

```sql
create type project_role as enum ('viewer', 'resumer', 'admin'); -- order is significant
```

```sql
-- STABLE SECURITY DEFINER — evaluated once per statement, not once per row
create or replace function has_role(p_project_id uuid, p_min_role project_role)
returns boolean
language sql
security definer
stable
set search_path = public
as $$
  select exists (
    select 1 from project_members
    where project_id = p_project_id
      and user_id = auth.uid()
      and role >= p_min_role
  );
$$;
```

```sql
-- resumer+ can pull a session's chunks; viewers can list but not pull
create policy "resumer_can_read_chunks" on session_chunks
  for select to authenticated
  using (has_role((select project_id from sessions where id = session_id), 'resumer'));
```

- Every policy has a comment naming which row of the access table (Doc §"Who can do what" / `auth.md`) it implements.
- Policies are per role and per action (select/insert/update/delete); both `update` and `insert` policies carry `with check`.
- Never disable RLS to debug. Query as the role in question, or use the pgTAP suite.
- **Never** inline `EXISTS (select 1 from project_members …)` in a policy — always go through `has_role()`, so the stability guarantee (one lookup per statement) holds everywhere.

`is_any_project_admin()` (CO-410) is `has_role()`'s own sibling for a genuinely different question: not "admin of *this* project" but "admin of *any* project at all" — the gate the web app's `/admin` console (auth.md) uses, since that console manages the whole fleet, not one project. Same `stable security definer` shape, same reason. Used in exactly one policy today (`agent_heartbeats`'s own admin-read policy) — don't reach for `has_role()` where the real question is this one instead.

`search_sessions(p_query_embedding, p_query_text, p_project_id, p_match_count)` (CO-501) is the one function in this file that is deliberately **not** `security definer` — every other function above is a boolean check *used inside* a policy, but this one itself returns real `sessions`/`session_passages` rows, so running it as the table owner (what `security definer` does) would silently bypass RLS rather than enforce it. Left as the default `security invoker`, called by the `search` Edge Function via the **caller's** own client — RLS on `sessions`/`session_passages` is what actually scopes a caller's results, same reasoning as `list-sessions`/`get-manifest`/`delete-session`'s own architectural shift (`edge-functions.md`). Its own two-CTE structure (`nearest_passages` — a plain top-K `order by embedding <=> query limit 200`, which the HNSW index serves directly — then `best_passage`, a cheap `distinct on` over that bounded 200-row set) exists so a "best match per session" query doesn't defeat the index the way a naive `distinct on (session_id) order by session_id, embedding <=> query` would. No `revoke execute ... from public` here (unlike `end_idle_sessions` below) — `search_sessions` *should* stay callable by any authenticated caller over PostgREST; RLS, not a function-level revoke, is the real narrowing. Verified directly (not just by pgTAP): a non-member of a session's project gets zero rows from `search_sessions`, and the session's own owner/project-member gets the real row — `supabase/tests/database/session_passages_rls.sql`.

`find_sessions_by_file(p_path, p_project_id, p_limit)` (CO-502) is the same `security invoker` pattern, one table over: `sessions.files_touched` gets a plain GIN index (`sessions_files_touched_gin_idx`, default `array_ops` — accelerates a real `@>`/`&&`/`=` containment query, though this function's own prefix-capable query doesn't happen to use it, see the migration's own comment) and this function finds every session whose `files_touched` has an element starting with `p_path` — a plain `left(f, length(p_path)) = p_path` comparison inside `exists (select 1 from unnest(...) f ...)`, deliberately **not** `f like p_path || '%'`: a real file or directory name can contain `%`/`_`, both LIKE wildcards, and a prefix check has no wildcard semantics to leak. Called from both `modules/sessions/data/queries.ts`'s `findSessionsByFile` (the web app's own "File touched" filter) and `list-sessions`' own `file` input (`carryon ls --file <path>`) via the caller's own client — RLS, not this function, is what actually scopes a caller's results in both cases, same as `search_sessions`. Matching as a prefix (rather than a separate exact-mode flag) covers both of the ticket's own testing cases with one query, since an exact path is trivially a prefix of itself. **Files_touched normalization** (the ticket's other own testing point, "paths are normalized relative to the repo root, so different machines match") happens earlier in the pipeline, not in this function: `_shared/condense-transcript.ts`'s own file-path extraction strips a session's `original_cwd` prefix before a path ever reaches `files_touched` — see that file's own comment and `summarize.ts`'s call site.

CO-504's five observability functions (`has_stale_agent_on_a_workday`, `lag_p50_seconds`, `lag_p95_seconds`, `fleet_upload_error_rate`, `abnormal_storage_growth_project_ids`, plus `project_storage_totals` for the storage-snapshot writer) are a different shape from every function above: they're real, pgTAP-tested SQL (same reasoning as `search_sessions`/`find_sessions_by_file` — keep the actual threshold logic testable without an HTTP round trip), but there's no end-user caller and so no RLS question to answer — they're revoked from `public` as an internal-implementation-detail boundary, not an access-control one. **The gotcha, found the hard way:** revoking from `public` does *not* leave `service_role` able to call them — verified directly (`set role service_role; select has_stale_agent_on_a_workday();` → `42501` until an explicit `grant execute ... to service_role` was added). This is the opposite of `end_idle_sessions` below, which is called directly by `pg_cron` as `postgres` (a superuser, which bypasses grants entirely) and so never needed one; these five are called via `check-observability-alerts`' own `admin.rpc(...)` — the service-role PostgREST client — so each one needs its own explicit `grant ... to service_role` right after its `revoke ... from public`. Any future SQL function meant to be internal-only, called through a service-role Edge Function rather than directly by `pg_cron`, needs the same pair, not just the revoke.

Every policy is tested with pgTAP for every role and every table (NFR-08, CO-302): a user without the role must get zero rows, never an error that leaks existence. Tests live under `supabase/tests/database/*.sql`, one file per table, run via `supabase test db supabase/tests/database --local` (wired into `ci.yml`'s `supabase` job). The standard harness for "run this query as role X": `set local role authenticated; set local request.jwt.claim.sub = '<uuid>';` inside the test's own transaction — `SET ROLE` (not just the session's original login role) is what RLS actually keys off, and `postgres` is permitted to assume `authenticated` the same way PostgREST's `authenticator` role does in production.
