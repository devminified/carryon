# CO-508 — Open-source release: status and validation checklist

## Done, verified with real tool runs — not assumed clean

- **Internal URLs, client names, credentials removed.** Searched the current working tree for any non-public URL pattern and any client-sounding name beyond this codebase's own long-standing fictional fixture (`acme-api`/`acme-project`, used consistently throughout `seed.sql`, Go tests, and TS tests as the example repo/client — not a real client). Found none. Every Slack-webhook-shaped URL in the codebase is a test fixture (`https://hooks.slack.com/services/T0/B0/x` and similar) that was never a real, working webhook. `supabase/config.toml`'s one `clerk.com` reference is the Supabase CLI's own generated scaffold comment about an optional third-party auth provider, unrelated to Devminified.
- **A real gitleaks scan of the full git history is clean.** `docker run zricethezav/gitleaks:v8.30.1 detect --source . --config .gitleaks.toml` → `no leaks found`, 83 commits / ~3.3MB scanned. The scan's first pass (no config) found 115 findings in the working tree and 27 across history — every one traced, by hand, to a specific already-documented value before being allowlisted in `.gitleaks.toml`: Supabase's own published local-dev demo credentials (identical on every machine that runs `supabase start` — never a real per-install secret), a CI-only throwaway Realtime encryption key for an ephemeral stack torn down at the end of every run, or a dynamically-generated/filler-based test fixture whose whole purpose is to look like a secret (the redaction engine's own corpus test, a freshly-generated RSA keypair in a GitHub App JWT test). None are real credentials. `.gitleaks.toml`'s own header comment documents this reasoning so a future contributor understands why each entry is there, rather than inheriting an unexplained allowlist.
- **A `gitleaks` CI job now runs on every PR** (`.github/workflows/ci.yml`'s `gitleaks` job), scanning each PR's own new commits — not `gitleaks/gitleaks-action`, which requires a paid `GITLEAKS_LICENSE` for an organization-owned repo (confirmed: `devminified` is a real GitHub Organization via `gh api orgs/devminified`, not a personal account) that nothing here has provisioned; the underlying open-source `gitleaks` CLI itself is free regardless, so the job installs and runs that binary directly.
- **License chosen: MIT** (the ticket's own recommendation), added as `LICENSE`.
- **`CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md` added**, each grounded in this repo's actual conventions (`.claude/rules/`) rather than generic boilerplate — e.g. `CONTRIBUTING.md` points at the real module checklist and testing matrix; `SECURITY.md` names the actual in-scope surfaces and references the real, already-written threat model.
- **A docs site added** (`docs/README.md` as the index): quick start (links to the README's own install walkthrough, which was already solid), `docs/architecture.md` (three trust zones, the pull/resume path, the four security layers — with new Mermaid diagrams, since no earlier diagram asset existed to reuse), self-hosting (links to the already-existing, already-thorough `deploy/selfhost/README.md` rather than duplicating it), and `docs/faq.md`.
- **Issue templates and a PR template added** (`.github/ISSUE_TEMPLATE/bug_report.md`, `feature_request.md`, `config.yml`; `.github/PULL_REQUEST_TEMPLATE.md`).
- **Public GitHub Actions**: already true and already verified continuously — `devminified/carryon` is a public repo (`gh repo view --json visibility` → `PUBLIC`) and every CI job (`lint`, `test` on three OSes, `supabase`, `web`, `web-e2e`, `cross-compile`, `selfhost-e2e`) already runs on public GitHub-hosted runners with no private secrets required for the basic build/test path — confirmed by `ci.yml`'s own env block, which uses only Supabase's published local-dev demo keys.
- **"A fresh clone builds and tests with no private access"** — verified directly: cloned `https://github.com/devminified/carryon.git` into a scratch directory (a genuine anonymous clone, not a local path), ran `go build ./...` and `go vet ./...` clean, and ran the subset of Go tests that need no local service (`internal/redact`, `internal/project`, `internal/claudepath`) — all pass. The full e2e test and the rest of the suite need a local Supabase instance (`supabase start`, Docker) — exactly as documented in the README's own "Development" section, the same thing CI itself does on a fresh runner with no special access.
- **Launch post drafted** — `docs/launch-post.md`, about the urgent-handoff problem per the ticket's own framing. Not published anywhere; that's a human call on timing and venue.

## Not done, and why — human-only validation points

- [ ] **Legal approves the license and the trademark use of "Devminified Carryon."** This PR picks MIT and writes "Devminified" into the `LICENSE` file's copyright line and this doc, but a real legal sign-off on using the company name publicly in an open-source project, and on MIT specifically (versus, say, Apache 2.0's patent grant), is not something to self-certify. Flagging it here, unchecked, the same way CO-507's CTO sign-off and CO-505's cost-report approval were flagged rather than assumed.
- [ ] **An outside developer gets from the README to a working local install in under 30 minutes.** This needs a real person who didn't build Carryon, a stopwatch, and the README as it actually reads to someone with no prior context — not something achievable by the same people who wrote the README judging their own instructions. The README's install path was re-read end to end as part of this ticket and nothing jumped out as missing, but that is not the same thing as this validation point passing.

## A note on scope

The Devminified production deployment's own config (real staging/production Supabase project refs, real GitHub App credentials, real client project names if any ever existed) was never in this repo to begin with — per the ticket's own framing, that lives in a private config repo. There was nothing to go back and scrub out of history because nothing like that was ever committed here; the gitleaks history scan above exists to verify that claim with a real tool, not just to repeat it.
